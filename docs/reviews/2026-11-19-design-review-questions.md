## 二、阻塞问题的处置详情

### B1. `BatchContext` 的构造时机与内容自相矛盾

冲突表述：

| 出处 | 表述 |
|---|---|
| §3.10.4 | `BatchContext` = params + cache + verdicts，「**在 worker 里构造**（缓存就绪之后）」；encoder cache 走已有的 `cache_rx` 通道 |
| §3.10.5（原） | 「BatchContext 保存**接纳时**的有效参数和能力快照」 |
| §3.11.1（原） | 「BatchContext **在批次接纳时**固定有效配置」 |

代码证据：`rencoder_lib/src/pipeline/context.rs:45`（`BatchContext { params, cache, verdicts }`）。

**判定**：选 C 案 —— 接纳时冻结有效配置，worker 在执行前取得当时可用的能力快照，再用两者构造 `BatchContext`；同一批固定使用该能力代次。cache 留在上下文里，不必移出，也不新增上下文类型。

**现文档措辞**（§3.11.1）：

> 批次接纳时冻结有效配置。worker 在开始执行前取得能力快照，再用两者构造 `BatchContext`。整批固定能力代次，批内运行时判定可以更新。

### B2. 探测代次没有进 §3.10.1 的共享状态清单

项目 CLAUDE.md 复盘清单明写：「并发结构更新 = 同一次提交里更新 §3.10.1 的共享状态清单和线程列表」。

**判定**：成立，补入共享状态清单。两种机制用途不同，不要合并成一套：

| 机制 | 解决什么 |
|---|---|
| 重检请求序号 | 探测乱序：较早的结果不得覆盖较新的结果 |
| 能力代次 | 旧批回报：上一代次跑出来的判定不得污染新一代次 |

**现文档措辞**（§3.10.1 目标段）：

> actor 单写探测请求序号及已发布能力代次。探测线程返回带请求序号的候选结果，actor 校验序号后统一发布结果和安排持久化，旧结果不得覆盖新快照或新磁盘缓存。执行 worker 在构造上下文时读取一次同代的能力和运行时判定，批内更新本地判定，回传携带代次。actor 只合并当前代次的回报。重检失败保留当前快照并反馈对应操作。

### B3. §8 的交叉引用指向不存在的章节

| 位置 | 修正前 | 修正后 |
|---|---|---|
| §8 #85 | 「（**§3.11.4 E1**）」，而新版 §3.11.4 已是「结果：保留已完成工作」，E1..E4 编号整体消失 | 改为 §3.11.3 |
| §8 #77 | 「任务模型**四条要求**（§3.11）」 | 「任务模型与执行契约（§3.11）」，状态改 future |

**未采纳**：首轮建议的「每条验收条件绑定当前代码问题点的行号」。理由是行号会漂移，绑定后必然失效；同一目的改用函数名/缺陷描述承载即可。

### B4. 「指纹」一词与被撤销的概念撞名

§3.10.6 原写「磁盘缓存使用 FFmpeg 指纹」「同指纹复用」，而 §8 #81 刚撤销「给产物写指纹」。

**判定**：改名「能力缓存匹配键」，并声明只用于能力缓存。

**撤回**：首轮建议的 build id 命名 —— 匹配键由探测到的信息计算，不是 FFmpeg 提供的正式标识，叫 build ID 会被误解。

### B5. schema 层无法表达「显式 vs 缺省」

**首轮结论有误**：原文把「`crf` 缺省得 45 与显式 0」当作不可区分的例子，实际二者本来就能区分（默认 45 ≠ 0）。真正会丢失的是「缺省与显式写 45」的区别，而这只在**来源**上有意义，行为上无差别。

重新推导后，真正需要保留存在性的只有「缺省与显式结果不同」的字段：

| 字段 | 缺省 vs 显式 | 是否需要存在性 |
|---|---|---|
| `extensions` | 默认列表 vs 空列表（= 全部） | 需要 |
| `ffmpeg_args.pre_input` / `post_input` | 默认 flag 列表 vs 显式 `[]` | 需要 |
| `crf` | 45 vs 0（码率模式） | 需要（多义标量）；缺省 vs 显式 45 不需要 |
| `max_batch_size` | 5000 vs 显式 5000 | 可有可无 |

代码证据：`rencoder_lib/src/config/app.rs:246,250` —— `pre_input` / `post_input` 是裸 `Vec`，是当前唯一会丢存在性的字段；`extensions` 与 `ffmpeg_args` 的其余子字段已是 `Option`。

**现文档措辞**（§3.10.5）：

> schema 层仅对需要区分缺省的字段保留存在性：只有「缺省」与「显式写出」会得出不同结果的字段才需要——集合类（`extensions` 的空列表与默认列表含义不同，`ffmpeg_args` 的 `pre_input` / `post_input` 显式空列表与缺省含义不同）与多义标量（如 `crf = 0` 表示码率模式）必须保留；其余标量（如 `crf` 缺省得 45 与显式写 45 解析结果相同）保留存在性只为区分来源，可有可无。

## 三、风险问题的处置详情

### R1. 临时文件会被下一轮采集当成输入

事实链：

1. 输出与输入**同目录**：`output_path_for` 用 `parent.join(...)`（`rencoder_lib/src/utils/fs.rs:55`）。
2. §3.11.2 要求临时文件同目录、保留容器扩展名。
3. `collect_dir` 只按扩展名 allowlist 过滤，**不排除隐藏文件**（`rencoder_lib/src/collect.rs:59`）；扩展名为空时等于收一切。

**判定**：临时文件前缀 `.rencoder-tmp.`；目录采集排除该前缀（即使未设扩展名过滤）；陈旧文件的清理判据见 C。

### R2. Windows 的提交语义

`std::fs::rename` 在 Windows 上走 `MoveFileExW` + `MOVEFILE_REPLACE_EXISTING`，能覆盖已存在目标；目标被其他进程占用时直接失败（sharing violation）。

**判定**：**驳回** remove + rename —— 第二步失败就会丢失原输出。设计改为「同卷替换操作，替换失败保留旧结果」，并禁止先删旧目标再重命名。验收覆盖目标已存在、目标被占用、替换失败三类，以各平台实际文件系统语义为准。

补充：这条不需要给 `rencoder_lib` 加 `windows-sys`（该依赖目前只在 CLI 侧）。

### R3. CLI 的信号路径与 GUI 不是同一条路

- CLI 走 `transcode_batch`（`rencoder_cli/src/main.rs:226`），GUI 走 actor（`rencoder_ui/src/app.rs:61`）。
- CLI 的 signal handler 是 `process::exit(1)`（`rencoder_cli/src/signal.rs:102`），既不写记录也不杀子进程。

**判定**：CLI 与 GUI 共享取消契约和进程监督，CLI 继续直接调用执行层。

### R4. `BatchReport` 与事件协议的关系

**判定**：执行层组装唯一的报告，CLI 直接消费，actor 以该报告生成带批次 ID 的终态事件。

### R5. `RequestId` 只对 GUI 有意义

**判定**：限定为 GUI 命令提交方；CLI 直接调用共享执行层。

### R6. GUI 侧的语义变更

现状：GUI 只有一个 `config_draft: AppConfig`（`rencoder_ui/src/msg.rs:196`），加载时整体克隆（`app.rs:73`），编辑时原地改；`msg.rs:1045` 把 draft 当成文件层。

**判定**：基线 = 最近加载或保存成功的文件配置；未保存的显式编辑 = 本次入口覆盖；保存成功才更新基线，失败保留基线和草稿；保存回执只清除该次已保存的编辑。

实现形状（归 §8 #86，不进设计正文）：基线 + 草稿 + 逐字段修订号；保存回执只清除 ≤ 该修订号的 dirty 标记。

### R7. 预演失效的判定依据

**判定**：复用预演前比较任务清单、有效规划参数和相关能力代次；预演做过媒体探测的，启动前还要检查输入是否变化，无法确认时重新规划。

## 附：状态文件协议整体替换的成本分析（2026-11-22）

把 actor 的命令/事件通道换成"轮询状态文件"的整体替换。**这里只记成本，不改设计** ——
设计要不要这么做，是另一个决定。

### 一句话结论

**换的是"运输"，不是"行为"**：批循环、忙闸、取消时机、NVENC 回退、能力判定全部不动。
成本集中在协议面（枚举、测试、文档），不在编码逻辑。

### 消失的机制

| 现在的机制 | 文件化之后 |
|---|---|
| `Command`（7 变体）+ `Event`（12 变体） | 两个结构体（命令 + 状态） |
| actor 的 `select!`（命令通道 + done 通道 + 修正通道） | 一个轮询循环 |
| 事件丢弃计数 `DropCounter` | 没了——状态永远是最新的 |
| 忙闸门 | 状态的 phase |
| GUI 的阻塞 recv 事件泵线程 | 轮询线程 |
| 取消令牌 | 命令/状态里的一个字段 |

`job.rs`（2900 行）+ `msg.rs`（2500 行）里，这两块是最大的头。

### 新增的机制

| | 规模 | 风险 |
|---|---|---|
| 状态 + 命令的结构体（JSON + `deny_unknown_fields` + 版本号） | 小，一次性 | 低（严格 schema 挡得住字段拼错） |
| 原子写（tmp + rename，仓库已有这个模式） | 小 | 低 |
| 轮询循环（流程侧 + 前端侧） | 中 | 低 |
| 命令槽 + 应答（id 回写） | 中 | **高**——唯一的正确性风险点 |

### 不会变简单的地方

- 忙闸门的**规则**（只是搬进状态）
- "每批恰好一个终态"（变成 phase）
- GUI 的 toast（状态驱动；"只弹一次"要 GUI 自己记，是 UI 侧的事，不是文件的事）
- **命令丢不丢**：现在靠 FIFO，文件没有顺序，靠应答纪律补。这**不是时限问题**，
  是正确性问题——命令丢了 → 流程永远不做那件事，不是"晚点做"。

|---|---|

### 真实的收益

1. **状态可读**：`cat state.json` 就知道这批跑到第几个文件、卡在哪。现在这信息散在
   事件流里，进程一挂就没了。
2. **前后端彻底解耦**：前端不再需要"懂" lib 的事件枚举；Tauri UI 跨进程读文件就行。
3. **取消的时限保证与平台无关**（见下）。

### 建议的切法（按风险从低到高）

```
第 1 刀  取消走文件              ← 已采纳
         验：文件机制 ✅ 原子写 ✅ 时限 ✅
第 2 刀  状态侧：流程写进度/阶段 → 前端轮询
         事件 → 状态字段
第 3 刀  命令侧：前端写命令 → 流程读
         命令槽 + 应答（风险最高，放最后）
```

每刀独立可用；到第 3 刀时文件机制已经被验过两轮。

### 第 1 刀（取消走文件）的成本

| 位置 | 改动 |
|---|---|
| lib `pipeline/cancel.rs` | 令牌多一个"盯着的文件"（`is_cancelled()` = 标志 **或** 文件在） |
| lib `config/path.rs` | 取消文件的路径解析（app 目录 + 环境变量覆盖——测试隔离要用） |
| CLI `signal.rs` | 回调/信号处理改成写文件（平台差异缩到"捕获 → 写文件"一行） |
| CLI `main.rs` | 批启动时删掉遗留的取消文件（否则上次的中断会取消下一次） |
| 测试 | 一个跨平台的 e2e（写文件 → 批停 → 记录在）+ 一个 Unix 的信号 e2e（保信号路径的覆盖） |

约 40 行 + 2 个测试。

它**不**解决的：信号捕获本身还是平台特定（Unix 三个信号 / Windows 五个控制台事件）——
"回调必须返回 TRUE，否则被默认处置杀掉"那个修复仍然需要，因为 Ctrl-C 那条路还在。

### 这一刀的风险点

| 风险 | 处理 |
|---|---|
| 遗留的取消文件——上次的中断会取消下一次 | 批启动时删掉 |
| 每次轮询多一次 stat | 轮询间隔 50ms → 20 次/秒，可忽略 |
| 文件被读到半截 | 只看**存在与否**，内容无所谓——半截也是"存在" |
